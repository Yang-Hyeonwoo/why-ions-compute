P3. 손바닥 보드로 만드는 측정·판단 장치

소스미터·PC 없이, 작은 board와 회로가 전압을 걸고 전류를 읽고 답을 낸다

무엇을 하나 손바닥만 한 board(NU40 DK)에 작은 module 몇 개를 꽂아, ① board가 전압을 걸고 → ② 소자에 전류가 흐르고 → ③ 회로가 전류를 읽고 → ④ board가 스스로 판단해 불·소리로 알리는 장치를 만듭니다. board에 코드를 넣는 일은 Arduino IDE로, PC에서 도는 일(기록 정리·학습·board용 파일 만들기)은 P1처럼 VS Code 실습 파일 7개를 ▷로 돌려서 합니다. 실습 파일은 모두 board 없이(mock) 먼저 돌려 볼 수 있습니다.

이 프로젝트를 끝내면 얻는 것 (1) 첫날: board가 보낸 숫자가 PC 화면에 0.5초마다 찍히는 것. (2) 내 손으로 친 버튼 리듬의 CSV 파일 하나와 "마지막 순간만 보고 리듬을 맞힐 수 있나"를 비교한 정확도 그림. (3) 100 kΩ 저항으로 잰 전압·전류 표(소스미터 값과 몇 % 안에서 맞는지). (4) board가 PC 없이 혼자 낸 판단 24개와 맞힌 비율(숫자 하나).

왜 하나 P2에서는 책상 위 큰 장비(소스미터)와 PC가 전압을 걸고 전류를 읽었습니다. 그 일을 작은 board와 부품 몇 개가 대신할 수 있을까요? 된다면 몸에 붙이는 패치처럼 작은 장치가 됩니다. 그때 정확도·시간·에너지가 어떻게 달라지는지를 숫자로 봅니다.

힌트이 프로젝트의 완료 기준

오늘 할 첫 실험은 P3.1입니다. board 1개와 데이터용 USB 케이블만 있으면 됩니다(1–2시간). PC 화면에 board가 보낸 숫자가 찍히면 그날은 끝입니다. 안 되더라도 어느 단계에서 어떤 메시지가 났는지 적으면 그날은 끝입니다. board가 오기 전에도 VS Code 실습 1–7은 mock으로 먼저 해 볼 수 있습니다.

P3 전체가 끝났다고 볼 때: 측정 회로 검증에서 저항·RC를 잰 값이 소스미터와 맞고(수준 2), PC 없이 판단에서 같은 저장 feature에 대해 board와 Python의 점수가 일치하면 끝입니다. 소자를 다시 측정한 정확도가 P2와 같을 필요는 없습니다. 재측정하면 소자 state가 달라질 수 있으므로, 그 차이 자체를 기록합니다.

경고이 페이지의 코드·회로 상태 (꼭 읽을 것)
  • VS Code 실습 7개의 코드·TERMINAL 출력·그림은 MOCK = True(board 없이)로 실제로 돌려 받은 것입니다. MOCK = False(진짜 board)로 바꾼 길은 아직 실물에서 돌려 보지 않았습니다.
  • firmware(firmware/)는 NU40 DK용 컴파일만 확인했고(2026-11-02, NUBoards nRF52 1.0.2), board Upload와 실물 시험은 아직입니다. 회로는 설계안이고, 보호 기능(입력 거부, 범위 밖 전압 거부, DAC 쓰기 실패 시 중단)도 코드에만 있습니다.
  • 그래서 Serial Monitor 화면과 진짜 board로 돌린 실습 화면은 코드의 출력문을 읽어 예상한 모양이며, 제목에 "예상 (실물 미검증)"이라고 적었습니다. 숫자는 board마다 다릅니다.

이야기부터: 큰 장비의 일을 작은 board가

P2를 떠올려 보세요. 소자 하나를 재려면 소스미터라는 큰 장비가 전압을 걸고, 전류를 읽고, PC가 그 숫자를 받아 판단했습니다. 좋은 장비이지만 책상 하나를 차지하고, 전기를 많이 쓰고, 몸에 붙일 수는 없습니다.

이 프로젝트는 그 세 가지 일(전압 걸기, 전류 읽기, 판단하기)을 손바닥만 한 board와 부품 몇 개에게 나눠 맡깁니다. 전압은 DAC라는 작은 칩이 걸고, 전류는 op-amp로 만든 회로가 전압으로 바꾸고, ADC라는 칩이 그 전압을 숫자로 읽고, board가 저장된 weight로 판단해 LED·부저·OLED로 알립니다. 맨 위 모식도의 ①~④가 이 흐름입니다.

중요한 한계가 하나 있습니다. 만드는 것은 미리 저장해 둔 입력을 재생해 소자에 걸고 판단·알림하는 breadboard 시제품입니다. 심장 신호를 실시간으로 받아 처리하는 장치가 아닙니다. 그것이 되려면 무엇이 더 필요한지는 P3.8에서 따로 계산합니다.

소스미터가 하던 일을 무엇이 대신하는지, 무엇이 달라지는지를 한 표로 적어 둡니다. 용어는 아래 단계에서 하나씩 풀이합니다.

소스미터·PC가 하던 일 P3에서 맡는 것 다른 점
전압 걸기 MCP4725 DAC + 1.65 V 기준 전압 범위가 좁고(이상적으로 ±1.65 V), 전원 켜질 때 state를 직접 관리해야 함
전류 재기 션트 저항 또는 TIA + ADS1115 측정 범위·속도가 회로 값으로 고정됨
전류 제한(compliance) 없음. 직렬 저항 R_lim이 최대 전류의 상한만 묶음 소스미터처럼 전압을 자동으로 낮추지 않음
pulse 순서·mask·판단 board(NU40 DK) 코드 실제 pulse 길이를 측정해 기록

기준 board 정하기

자동차로 치면 board는 엔진이고, 측정 회로는 바퀴와 브레이크입니다. 엔진을 비싼 것으로 바꿔도 바퀴가 헛돌면 차는 똑바로 못 갑니다. 이 프로젝트의 어려운 부분도 MCU가 아니라 아날로그 측정 회로(전류 범위, noise, 속도)입니다. 비싼 board가 미검증 회로 문제를 해결하지는 않습니다. 그래서 MCU는 예제가 가장 많은 것 하나를 기준으로 정하고, 측정 회로에 집중합니다.

board (개발 보드): 작은 컴퓨터 칩, USB 단자, LED, 버튼이 손바닥만 한 기판 하나에 올라 있는 것. 우리 코드를 넣으면 그 코드대로 움직입니다.

MCU (microcontroller): board 가운데 붙은 작은 컴퓨터 칩. PC보다 수천 배 느리지만 전기를 아주 적게 씁니다(동전 전지로도 돌 정도).

아날로그 측정 회로: 전류처럼 "연속으로 변하는 양"을 숫자가 되기 전에 다루는 회로. 예: 소자에 흐르는 0.000001 A를 ADC가 읽을 수 있는 1 V 정도의 전압으로 바꾸는 회로.

후보 장점 확인할 것 / 상태 이 프로젝트에서
NU40 DK (nRF52840) 저전력 블루투스(BLE)에 강하고, Arduino IDE로 씀. board에 LED 4개·버튼 4개 board package 'NUBoards nRF52 by NUCODE'(Adafruit nRF52 코어를 바탕으로 한 것), I²C = P0.26·P0.27 [board package] 기준 플랫폼 (코드 묶음의 firmware)
ESP32 DevKitC (ESP32-WROOM-32E) 예제가 가장 많고 와이파이가 있음 firmware는 같은 파일이 ESP32에서도 컴파일되도록 #if로 나눠 두었음(ESP32용 컴파일은 미확인) 와이파이가 필요해질 때만
계측 중심 대안: 전기화학용 AFE 평가보드(예: ADI AD5940/AD5941 계열), 소형 USB 퍼텐쇼스탯 module(예: PalmSens EmStat Pico) nA 측정·전위 제어가 이미 검증된 하드웨어 사양·가격·소프트웨어·전압 범위 미확인 전류가 10 nA 아래로 작거나 breadboard TIA가 맞지 않을 때 연구비로 검토

BLE (Bluetooth Low Energy): 전기를 적게 쓰는 블루투스. 이 프로젝트에서는 board가 휴대폰에 판단 결과 알림을 보낼 때 씁니다.

I²C: 칩끼리 전선 두 가닥(SDA = 데이터선, SCL = 시계선)으로 숫자를 주고받는 약속. 한 줄 전화선에 여러 집이 매달린 것처럼, DAC·ADC·OLED가 모두 이 두 선에 같이 매달립니다.

NU40 DK로 바꾸면서 달라진 것은 board에 붙은 부분뿐입니다. 측정 회로(DAC·ADC·TIA), pulse 순서, PC 쪽 Python 코드, 단계 순서는 그대로입니다.

  • 꽂는 것: USB 한 가닥. 핀에는 아무것도 안 꽂음(LED1·버튼1은 board에 붙어 있음).
  • 정상 값: LED1이 0.5 s마다 깜빡임. Serial Monitor 숫자가 500씩 늚. 버튼1을 누르는 동안 btn = 1.

먼저 Tools → Port에 COM 번호가 있는지(없으면 충전 전용 케이블), 그다음 baud가 115200인지 봅니다.

저항·R–C (R–C 첫 배선)

  • 연결 전 상태: USB 뺌. breadboard는 비어 있음. rail이 가운데서 끊겼는지 멀티미터로 확인해 둠.
  • 꽂는 것: P1.04 → 10행 a, A0 → 14행 a, GND → 위 − rail. 100 kΩ: 10행 c ↔︎ 14행 c. 10 µF: + 14행 d, − 15행 d. jumper: 15행 a ↔︎ 위 − rail.
  • 정상 값: tau measured 0.8–1.2 s (100 kΩ × 10 µF = 1.0 s). 충전 끝 A0 ≈ 3.3 V, 1 s 시점 ≈ 2.1 V.

모두 0 V 근처 → P1.04 선과 10행. 처음부터 3.3 V 근처 → A0 선이 14행이 아니라 10행에 있음. 값이 튐 → 15행–rail–GND 선.

DAC·ADC (P3.2–P3.3)

  • 연결 전 상태: USB 뺌. R–C 부품·선은 뽑음(같은 행을 씀). board 3.3V·GND → 위 + rail·− rail.
  • 꽂는 것: 두 module의 VCC·GND → rail, SDA → P0.26, SCL → P0.27, ADC ADDR → GND, DAC VOUT → ADC A0.
  • 정상 값: I²C 스캐너에 주소 2개(0x48, 그리고 0x60–0x63 중 하나). DAC 코드 2048 → 멀티미터와 ADC 모두 약 1.65 V(서로 수십 mV 안).

주소가 하나도 없으면 SDA·SCL이 바뀌었는지, GND가 이어졌는지. 하나만 나오면 안 나온 module의 VCC·GND 행.

전류 측정 회로 (P3.4)

  • 연결 전 상태: USB 뺌, J1 뺌. DAC·ADC 배선은 그대로 두고 DAC VOUT–ADC A0 선만 뺌.
  • 꽂는 것: MCP6002(30–33행, 가운데 홈 걸침), 10 kΩ 두 개 + 1 µF(36행), R_f·C_f, R_lim(40–44행), J1(44–45행). 소자 자리 = 45행 ↔︎ 49행.
  • 정상 값: 켠 뒤 READY VREF= 1.4–1.9 V. 소자 자리에 100 kΩ, s 명령 → +0.5 V 줄에서 약 +5000 nA(기대값과 몇 % 안). 0 V 줄은 몇 nA(op-amp 오프셋).

E,-1,io_init → I²C 주소와 A3의 V_ref부터. [포화] → R_f가 너무 큼. 전류가 일정 비율로 틀림 → R_f 실제 값과 DAC 보정.

할 일 board는 USB로 꽂아 둔 채입니다.

  1. Arduino IDE 위쪽 메뉴 File → New Sketch를 누릅니다. 새 창이 하나 더 열리고, 탭 이름이 sketch_nov6a.ino처럼 되어 있습니다. 이 새 창에서 계속합니다.
  2. 흰 편집 창 안을 한 번 클릭하고 Ctrl+A(모두 선택) → Delete. 미리 적혀 있던 void setup() { … } 글이 모두 지워져 빈 창이 됩니다.
  3. 아래 코드 상자 오른쪽 위의 복사 아이콘을 누릅니다.
  4. 빈 편집 창을 클릭하고 Ctrl+V. 코드가 그대로 들어가면 됩니다.
#include <Adafruit_TinyUSB.h>  // NU40: USB 시리얼(Serial)을 쓰려면 필요 (없으면 링크 오류)
void setup() {
  Serial.begin(115200);
  while (!Serial && millis() < 3000) delay(10);  // USB 시리얼이 열릴 때까지 최대 3초
  pinMode(LED_BUILTIN, OUTPUT);                   // NU40: LED1 (P0.13)
}
void loop() {
  digitalWrite(LED_BUILTIN, !digitalRead(LED_BUILTIN));
  Serial.println(millis());
  delay(500);
}

뜻: "켜지면 USB 통신을 115200으로 열고, 0.5초마다 LED1을 뒤집고 지금 시각(ms)을 한 줄 보내라." 이 코드는 NU40용으로 컴파일을 확인했습니다(Upload는 미확인).

millis(): board가 켜진 뒤 지난 시간을 1/1000초(ms) 단위로 세는 값. 켜고 3초 뒤면 3000. 이 코드는 이 숫자를 0.5초마다 PC로 보냅니다.

질문. board를 PC에서 뽑아 USB 보조배터리에 꽂으면 LED1은 어떻게 될까요? 다시 PC에 꽂고 Serial Monitor를 열면 숫자는 몇부터 나올까요? 먼저 적어 본 뒤 정답을 봅니다.

LED1은 계속 0.5초마다 깜빡입니다. 코드(firmware)는 board 안에 들어 있어서, 전기만 들어오면 PC가 없어도 돕니다. Serial Monitor는 "board가 보내는 글자를 PC가 엿보는 창"일 뿐입니다.

숫자는 PC에 다시 꽂은 순간부터 센 작은 값입니다. 예: 꽂고 10초 뒤에 Serial Monitor를 열면 10000 근처. USB를 뽑는 순간 전원이 끊겨 board가 꺼졌다가 새로 켜졌기 때문입니다. millis()는 "켜진 뒤 지난 시간"이라 켤 때마다 0부터 다시 셉니다.

관찰할 점. board는 PC 없이도 돕니다. 이것이 PC 없이 판단의 바탕입니다.

P3.1a. 버튼 리듬을 CSV로 남기기

P3.1에서 board가 숫자를 보냈다면, 이제 내 손이 만든 신호를 처음으로 파일에 남깁니다. board가 버튼1을 1초에 200번 들여다보고 "지금 눌렸나(1), 아니나(0)"를 한 줄씩 PC로 보내면, PC가 받아 CSV 파일에 적습니다. 부품은 더 사지 않습니다.

sampling rate 200 Hz: 1초에 200번, 곧 5 ms마다 한 번 버튼 state를 보고 한 줄씩 보냅니다. 40초 기록이면 40 × 200 = 8,000줄.

CSV: 숫자를 쉼표로 나눠 적은 글 파일. 엑셀로 열립니다. 우리 기록은 모두 이 형식입니다.

먼저 '실패 모양'부터 봅니다. 이 기록에서 나올 수 있는 실패는 세 가지이고, 실습 1이 이것들을 세어 줍니다.

bounce (접점 튐): 버튼을 뗄 때 속의 금속 조각이 아주 짧게 한 번 더 붙는 것. 공이 바닥에서 통통 튀는 것과 같습니다. 뗀 뒤 30 ms 안에 다시 붙은 누름은 버립니다.

dropped samples (빠진 줄): PC가 바빠서 board가 보낸 줄을 못 받은 구간. 줄 번호 n이 예를 들어 59 → 80으로 건너뜁니다.

saturation (포화): 측정값이 잴 수 있는 범위의 끝(여기서는 3.3 V나 0 V)에 붙어 평평해지는 것. 2 m까지만 적힌 자로 2.1 m인 사람을 재면 "2 m"로만 나오는 것과 같습니다.

#   t_ms : board가 켜진 뒤 지난 시간 (ms)
#   btn  : 버튼 1 = 눌림, 0 = 뗌
#   a0   : 빛 센서 값 (0–4095). 센서를 안 꽂았으면 아무 값
# ============================================================

FS = 200   # board는 1초에 200줄 (5 ms마다 한 줄)


def mock_board_lines(label, seconds, n_drop, seed=3):
    """가짜 board: 사람이 리듬을 친 것처럼 '200 Hz 줄'을 만든다 (실측 아님)."""
    rng = np.random.default_rng(seed)
    n_rhythms = int(seconds / 4.5) + 1              # 리듬 한 번 + 쉼 ≈ 4.5초 (넉넉히 만들고 SECONDS에서 자름)
    t, btn, light = b1_memory.synth_stream(label, n_rhythms, rng)
    keep = t < seconds
    lines = [f"{i},{3061 + round(t[i] * 1000)},{btn[i]},{int(light[i] / 3.6 * 4095)}"
             for i in np.where(keep)[0]]
    for _ in range(n_drop):                          # PC가 바빠 줄 20개(0.1초)를 못 받은 것처럼
        k = rng.integers(200, len(lines) - 200)
        del lines[k:k + 20]
    return lines

t = t - t[0]                                       # 기록 시작을 0초로
btn = np.array([r[2] for r in rows])
light = np.array([r[3] for r in rows])

# ============================================================

# 빠진 줄: 줄 번호 n이 1씩 늘지 않은 곳

# 누름 = 버튼이 0 → 1로 바뀐 순간, 뗌 = 1 → 0

release_t = t[1:][(btn[1:] == 0) & (btn[:-1] == 1)]

# 접점 튐(bounce): 뗀 지 30 ms 안에 다시 눌린 것 → 진짜 누름이 아니다
bounce_t = [p for p in press_t if np.any((p - release_t >= 0) & (p - release_t < 0.03))]
real_press_t = [p for p in press_t if p not in bounce_t]

# 빛 포화: 빛 값이 0 V나 3.6 V 끝에 붙은 줄 (센서를 안 꽂았으면 무시)
saturated = int(np.sum((light > 3.6 * 0.98) | (light < 0.02)))

if not real_press_t:

print()

print(f"dropped gaps          : {gaps}")
print(f"presses (0 -> 1)      : {len(press_t)}")
print(f"  bounces (< 30 ms)   : {len(bounce_t)}")
print(f"  real presses        : {len(real_press_t)}")

실습 2. leaky node 하나에 리듬 넣기 (p3_2_leaky.py)

소자를 가장 단순하게 흉내 낸 leaky node 하나에 리듬 X와 Y를 넣고, 마지막 누름 직후의 값 하나만 읽습니다. 그 숫자 하나로 X와 Y가 갈리는지 봅니다. 마지막 두 번은 두 리듬이 같으므로, 갈린다면 그것은 앞쪽 누름의 흔적 덕분입니다.

leaky node: 밑에 작은 구멍이 난 물컵. 누를 때마다 물을 붓고(값이 오름), 쉬는 동안 물이 새어 나갑니다(값이 줄어듦). 최근에 많이 누를수록 물이 많습니다.

time constant τ (타우): 흔적이 얼마나 오래 남는지. τ = 0.5 s면 0.5초 뒤에 물이 약 1/3로 줄어듭니다. 구멍이 클수록 τ가 짧습니다.

threshold (문턱): 비교 기준이 되는 값. 마지막 물 높이가 문턱보다 낮으면 X, 높으면 Y라고 답합니다. 문턱은 연습 기록을 보고 프로그램이 정합니다.

# 전체 과정:
#
#   리듬 X, Y: 둘 다 5번 누르고, 마지막 두 번(1.5 s, 2.0 s)은 똑같다
#         ↓
#   leaky node(구멍 난 물컵)에 넣기
#     누를 때마다 물을 붓고, 쉬는 동안 τ에 따라 물이 샌다
#         ↓
#   마지막 누름 직후의 물 높이(state) 하나만 읽기
#         ↓
#   [그림 왼쪽] X와 Y의 물 높이가 시간에 따라 어떻게 변하나
#   [그림 오른쪽] 손 떨림이 있는 리듬 N번씩: 마지막 물 높이로 X·Y가 갈리나?
#
# 맨 위의 TAU를 0.1 → 0.5 → 2.0으로 바꿔 Run 해 보는 것이 이 실습의 핵심입니다.
# board는 필요 없습니다.
# ============================================================

import sys
from pathlib import Path

import numpy as np
import matplotlib.pyplot as plt

CODE = Path(__file__).resolve().parent.parent      # ion-projects-code 폴더
sys.path.insert(0, str(CODE / "python"))           # 공용 코드 폴더를 찾을 수 있게

import b1_memory      # 리듬 X·Y의 정의, leaky node 계산 (P3.1b 공용 코드)


# ============================================================
# 0. 그림 설정 — 건드리지 않아도 됩니다
# ============================================================

plt.rcParams.update({
    "font.family": "Malgun Gothic", "axes.unicode_minus": False, "font.size": 11,
    "legend.frameon": False, "axes.spines.top": False, "axes.spines.right": False,
})


# ============================================================
# 1. 바꿔 볼 수 있는 설정값  ← 여기를 바꿔 보세요
# ============================================================

TAU = 0.5          # time constant τ (초): 흔적이 얼마나 오래 남나. 0.1, 0.5, 2.0 …
G = 0.5            # 한 번 누를 때 붓는 양 (빈 컵의 절반만큼)
N_TRIALS = 40      # 리듬마다 몇 번 쳤다고 칠까 (앞 절반은 연습, 뒤 절반은 시험)
JITTER = 0.08      # 손 떨림: 간격이 평균 몇 %씩 흔들리나 (0.08 = 8 %)
SEED = 1


# ============================================================
# 2. 두 리듬 (공용 코드 b1_memory.PAT에 적혀 있다)
# ============================================================

PAT = b1_memory.PAT       # {"X": [0, 0.25, 0.5, 1.5, 2.0], "Y": [0, 1.0, 1.25, 1.5, 2.0]}
for name in ("X", "Y"):
    print(f"rhythm {name}: press times {PAT[name]} s,  gaps {np.round(np.diff(PAT[name]), 2).tolist()} s")


# ============================================================
# 3. leaky node: 물 높이 x (0 = 빈 컵, 1 = 가득)
# ============================================================
#
#   누를 때       x ← x + G × (1 − x)          (남은 빈 공간의 G만큼 붓기)
#   쉬는 Δt 동안  x ← x × exp(−Δt / τ)         (τ초가 지나면 약 1/3로 줄어듦)
#
# b1_memory.leaky_state(누름 시각들, τ, G)가 이 계산을 하고
# "마지막 누름 직후의 x"를 돌려준다. 그림을 그리려고 아래에서 시간마다 x도 계산한다.
# ============================================================

def leaky_curve(times, tau, g, t_end=2.6, dt=0.005):
    """0초부터 t_end초까지 5 ms마다의 물 높이"""
    ts = np.arange(0, t_end, dt)
    xs = np.zeros_like(ts)
    x, last_t, k = 0.0, 0.0, 0
    for i, now in enumerate(ts):
        x *= np.exp(-(now - last_t) / tau)          # 새는 동안
        last_t = now
        while k < len(times) and times[k] <= now:   # 이 순간에 누름이 있으면 붓기
            x += g * (1 - x)
            k += 1
        xs[i] = x
    return ts, xs


# ============================================================
# 4. 손 떨림이 있는 리듬을 여러 번: 마지막 물 높이 모으기
# ============================================================

rng = np.random.default_rng(SEED)

def jittered(name):
    gaps = np.diff(PAT[name]) * rng.normal(1, JITTER, 4)      # 간격마다 조금씩 흔들기
    return np.concatenate([[0], np.cumsum(gaps)])

final = {name: np.array([b1_memory.leaky_state(jittered(name), TAU, G) for _ in range(N_TRIALS)])
         for name in ("X", "Y")}


# ============================================================
# 5. 문턱(threshold) 하나로 나누기: 연습 절반으로 문턱, 시험 절반으로 채점
# ============================================================

half = N_TRIALS // 2
v_train = np.r_[final["X"][:half], final["Y"][:half]]
y_train = np.r_[np.ones(half), np.zeros(half)]              # X = 1, Y = 0
th, sign = b1_memory.fit_threshold(v_train, y_train)          # 연습 문제를 가장 잘 나누는 문턱

v_test = np.r_[final["X"][half:], final["Y"][half:]]
y_test = np.r_[np.ones(N_TRIALS - half), np.zeros(N_TRIALS - half)]
acc = np.mean((sign * (v_test - th) > 0) == y_test)

print()
print(f"leaky node, tau = {TAU} s")
print(f"final state X : {final['X'].mean():.3f}  (min {final['X'].min():.3f}, max {final['X'].max():.3f})")
print(f"final state Y : {final['Y'].mean():.3f}  (min {final['Y'].min():.3f}, max {final['Y'].max():.3f})")
print(f"threshold     : {th:.3f}")
print(f"test accuracy : {acc:.0%}   (chance = 50%)")


# ============================================================
# 6. 그림
# ============================================================

fig, ax = plt.subplots(1, 2, figsize=(8, 3.9), gridspec_kw={"width_ratios": [1.6, 1]})
color = {"X": "#2b59c3", "Y": "#d9962a"}

for name in ("X", "Y"):
    ts, xs = leaky_curve(PAT[name], TAU, G)
    ax[0].plot(ts, xs, color=color[name], lw=1.8, label=f"리듬 {name}")
    ax[0].plot(PAT[name], np.full(5, -0.05 if name == "X" else -0.11), "|", color=color[name], ms=8, mew=2)  # 누른 시각
    end = b1_memory.leaky_state(PAT[name], TAU, G)
    ax[0].plot(2.0, end, "o", color=color[name], ms=7)
ax[0].axvline(2.0, color="0.6", ls=":", lw=1)
ax[0].text(2.03, 0.98, "여기서 한 번\n읽는다", va="top", fontsize=9.5, color="0.35")
ax[0].set_ylim(-0.15, 1.02)
ax[0].set_xlabel("time (s)   | = 누른 시각")
ax[0].set_ylabel("물 높이 (state)")
ax[0].set_title(f"τ = {TAU} s일 때 물 높이", loc="left")

for row, name in enumerate(("X", "Y")):
    ax[1].plot(final[name], np.full(N_TRIALS, row) + rng.uniform(-0.15, 0.15, N_TRIALS), "o",
               color=color[name], ms=4, alpha=0.7)
ax[1].axvline(th, color="#c0392b", ls="--", lw=1.3, label="문턱")
ax[1].set_yticks([0, 1], ["X", "Y"])
ax[1].set_ylim(-0.6, 1.6)
ax[1].set_xlabel("마지막 물 높이")
ax[1].set_title(f"{N_TRIALS}번씩: 시험 {acc:.0%}", loc="left")

fig.tight_layout(rect=(0, 0.08, 1, 1))
h0, l0 = ax[0].get_legend_handles_labels()
h1, l1 = ax[1].get_legend_handles_labels()
fig.legend(h0 + h1, l0 + l1, loc="lower center", ncol=3, bbox_to_anchor=(0.5, 0.0))

plt.show()

  • 3번 상자의 두 줄 규칙: 누를 때 x ← x + G × (1 − x), 쉬는 동안 x ← x × exp(−Δt/τ). 공용 코드 b1_memory.leaky_state가 같은 계산으로 마지막 값을 줍니다.

실습 3. 다섯 방법으로 맞히기 (p3_3_compare.py)

같은 버튼 기록을 다섯 방법으로 맞혀 보고, 어떤 방법에 기억이 필요한지 봅니다. 손 버릇은 날마다 다르므로 session s1·s2로 연습하고 마지막 s3로만 시험합니다. 지금은 synthetic data로 하고, 내 기록이 쌓이면 DATA 한 줄만 바꿔 같은 파일을 돌립니다.

비교하는 다섯 방법입니다. 화면에 나오는 영어 이름을 같이 적었습니다.

  • last value only: 마지막 누름 순간의 입력. 두 리듬 모두 1(눌림)이라 못 맞히는 것이 정상.
  • count & length: 누른 횟수(5)와 길이(2.0 s). 두 리듬이 같게 만들었으니 못 맞히는 것이 정상.
  • first-gap rule: 첫 간격 하나를 문턱과 비교하는 한 줄짜리 규칙(X 0.25 s, Y 1.0 s).
  • leaky node tau=…: 실습 2의 물컵. τ 세 가지.
  • reservoir 40 (slow / fast): 물컵 40개를 무작위로 이어 둔 것 + 학습한 readout. 흔적이 약 0.4초 남는 것(slow)과 약 0.07초인 것(fast).

reservoir: leaky node 같은 node 여러 개(여기서는 40개)가 무작위로 서로 이어져 입력을 섞어 두는 모형. node 사이 연결은 고정이고, 학습은 그 뒤의 readout만 합니다.

synthetic data: 컴퓨터가 수식으로 만든 가짜 기록. 여기서는 session 3개 × 리듬 2개 × 20번을 "쳤다고 치고", 박자를 조금씩 흔들고 bounce도 섞습니다. seed가 고정이라 언제 돌려도 같은 결과입니다.

train / test: 마지막 session의 기록은 연습(train)에 안 쓰고 시험(test)에만 씁니다. 같은 날 기록을 섞으면 그날의 손 버릇까지 외워 점수가 부풉니다.

chance: 한쪽 답만 찍었을 때의 정확도. X와 Y가 반반이면 50%입니다. 50% 근처 = 못 맞힌다, 100% = 다 맞힌다.

# ============================================================
# P3 실습 3 · 다섯 가지 방법으로 리듬 X·Y 맞히기
#
# 전체 과정:
#
#   버튼 기록 (처음엔 synthetic data: session 3개 × 리듬 2개 × 20번)
#         ↓
#   쉼이 1.6초보다 길면 끊어서 trial(리듬 한 번)로 나누기, bounce 버리기
#         ↓
#   session s1·s2로 연습(train), 마지막 session s3로 시험(test)
#         ↓
#   다섯 방법으로 채점:
#     last value only · count & length · first-gap rule
#     leaky node (τ 세 가지) · reservoir 40 (slow / fast)
#         ↓
#   [그림 1] 방법별 정확도
#   [그림 2] 시험 리듬만 빠르게·느리게, 손 떨림을 크게 하면?
#
# 내 버튼 기록이 session 2개 이상 쌓이면 DATA를 내 CSV로 바꿔 Run 합니다.
# ============================================================

import sys
from pathlib import Path

import numpy as np
import matplotlib.pyplot as plt

CODE = Path(__file__).resolve().parent.parent      # ion-projects-code 폴더
sys.path.insert(0, str(CODE / "python"))           # 공용 코드 폴더를 찾을 수 있게

import b1_memory as bm                # 리듬 나누기·다섯 방법 채점 (P3.1b 공용 코드)
from common import print_table        # TERMINAL에 표를 줄 맞춰 찍기


# ============================================================
# 0. 그림 설정 — 건드리지 않아도 됩니다
# ============================================================

plt.rcParams.update({
    "font.family": "Malgun Gothic", "axes.unicode_minus": False, "font.size": 11,
    "legend.frameon": False, "axes.spines.top": False, "axes.spines.right": False,
})


# ============================================================
# 1. 바꿔 볼 수 있는 설정값  ← 여기를 바꿔 보세요
# ============================================================

DATA = "synthetic"          # 내 기록으로: "runs/p3/b1_taps.csv"
TAUS = (0.1, 0.5, 2.0)      # 비교할 leaky node의 τ (초) 세 개


# ============================================================
# 2. 기록 읽기 → trial로 나누기
# ============================================================
#
# synthetic data = 사람이 X·Y를 20번씩 친 것처럼 컴퓨터가 만든 가짜 기록.
#   박자를 8 %쯤 흔들고, bounce를 10 %쯤 섞고, 가끔 한 번을 빼먹게 만든다.
#   SEED가 고정이라 언제 돌려도 같은 결과 (실측 아님).
# ============================================================

if DATA == "synthetic":
    rng = np.random.default_rng(7)
    streams = {}
    for session in ("s1", "s2", "s3"):
        for label in ("X", "Y"):
            t, btn, _ = bm.synth_stream(label, 20, rng)
            streams[(session, label)] = (np.round(t, 3), btn)
else:
    streams = bm.load(str(CODE / DATA))          # 내 CSV: session·label별로 읽기

all_trials, info = bm.trials(streams)             # (session, label, 누름 시각 5개) 목록
sessions = sorted({s for s, _, _ in all_trials})
if len(sessions) < 2:
    raise SystemExit("session이 2개 이상 필요합니다 (연습·시험을 session으로 나눔). 실습 1을 SESSION = 's2'로 더 기록하세요.")

test_session = sessions[-1]                        # 마지막 session은 시험에만
train = [x for x in all_trials if x[0] != test_session]
test = [x for x in all_trials if x[0] == test_session]

print(f"{'synthetic' if DATA == 'synthetic' else 'measured'} data: {len(all_trials)} trials "
      f"(train {len(train)}: {', '.join(sessions[:-1])} / test {len(test)}: {test_session})")
for k, v in info.items():
    print(f"  {k}: {v}")


# ============================================================
# 3. 다섯 방법으로 채점 (b1_memory.evaluate)
# ============================================================
#
#   last value only : 마지막 누름 순간의 입력 (X든 Y든 1)
#   count & length  : 누른 횟수(5)와 처음→마지막 길이(2.0 s)
#   first-gap rule  : 첫 간격 하나를 문턱과 비교 (X 0.25 s, Y 1.0 s)
#   leaky node      : 실습 2의 물컵. 마지막 누름 직후 물 높이 하나
#   reservoir 40    : 물컵 40개를 무작위로 이어 둔 것 + 학습한 readout
#                     slow = 흔적이 약 0.4초, fast = 약 0.07초
# 모든 방법이 train 기록만 보고 문턱·weight를 정하고, test 기록으로 채점한다.
# ============================================================

bm.TAUS = tuple(TAUS)                              # 공용 코드가 이 τ 목록을 쓰게
names = {"last": "last value only", "count": "count & length", "rule": "first-gap rule",
         **{f"tau{t}": f"leaky node tau={t} s" for t in TAUS},
         "esn": "reservoir 40 (slow)", "esn_fast": "reservoir 40 (fast)"}

esn = (bm.ESN(leak=0.05), bm.ESN(leak=0.3))        # 느린 reservoir, 빠른 reservoir
base = bm.evaluate(train, test, esn)
chance = max(np.mean([lab == "X" for _, lab, _ in test]), np.mean([lab == "Y" for _, lab, _ in test]))

print(f"chance (always guess the larger class): {chance:.0%}")
print()
print_table(["model", "test accuracy"], [[names[k], f"{v:.0%}"] for k, v in base.items()], left=(0,))


# ============================================================
# 4. 시험 리듬만 바꿔 보기 (연습은 그대로)
# ============================================================
#
#   tempo : 시험 리듬의 간격을 모두 ×0.5(두 배 빠르게) ~ ×2(두 배 느리게)
#   jitter: 간격마다 손 떨림을 0–30 % 더하기
#   새로 친 것이 아니라 기록된 시각을 계산으로 늘이고 흔든 것이다.
# ============================================================

mid_tau = f"tau{TAUS[1]}"
show = ("rule", mid_tau, "esn")                    # 세 방법만 비교
scales = [0.5, 0.7, 1.0, 1.4, 2.0]
jitters = [0.0, 0.1, 0.2, 0.3]
by_scale = {k: [bm.evaluate(train, bm.vary(test, scale=s), esn)[k] for s in scales] for k in show}
by_jit = {k: [bm.evaluate(train, bm.vary(test, jitter=j), esn)[k] for j in jitters] for k in show}

print()
print("test tempo changed (x interval; training stays at 1.0)")
print_table(["model"] + [f"x{s:g}" for s in scales],
            [[names[k]] + [f"{v:.0%}" for v in by_scale[k]] for k in show], left=(0,))

질문 1. last value only와 count & length는 왜 50%일까요?

두 리듬에서 그 숫자가 똑같기 때문입니다. 마지막 누름 순간의 입력은 X든 Y든 1이고, 횟수(5)와 길이(2.0 s)도 같게 만들었습니다. 두 리듬의 차이는 앞쪽 순서에만 있습니다.

질문 2. 그림 5 왼쪽에서 시험만 두 배 빠르게(0.5) 치면 first-gap rule도 50%로 떨어지는데, 두 배 느리게(2.0) 치면 100%입니다. 왜 한쪽만 버틸까요?

first-gap rule은 연습 때 정한 문턱(0.25 s와 1.0 s 사이)과 첫 간격을 비교합니다. 두 배 빠르게 치면 Y의 첫 간격이 1.0 → 0.5 s로 줄어 문턱보다 짧아질 수 있고, 그러면 Y도 X라고 답해 50%가 됩니다. 두 배 느리게 치면 X의 첫 간격은 0.25 → 0.5 s로 늘어도 아직 문턱보다 짧고, Y는 2.0 s로 더 길어지므로 계속 맞힙니다.

leaky node와 reservoir는 양쪽 다 무너집니다. 학습한 readout이 "원래 빠르기에서의 물 높이"에 맞춰져 있기 때문입니다. 실제로 쓰려면 연습 기록에 여러 빠르기를 섞어야 합니다.

질문 3. 이 과제를 푸는 데 reservoir가 꼭 필요할까요?

아닙니다. first-gap rule 한 줄로 95%, τ가 맞는 leaky node 하나로 95–100%가 나옵니다. 그래서 나중에 소자로 이 과제를 풀더라도 "한 줄 규칙이나 R–C 하나보다 무엇이 더 나은가"를 함께 보여야 합니다.

0 Ω 근처면 두 다리가 같은 행에 있거나 선이 10행과 14행을 직접 잇고 있습니다. 숫자가 안 나오면(OL) 저항 다리가 구멍에 덜 들어갔습니다.

P3.2–P3.3. DAC로 전압 만들고 ADC로 읽기

P2에서 소스미터가 하던 첫 번째 일은 "소자에 원하는 전압 걸기"였습니다. 이 단계에서는 그 일을 손톱만 한 칩 하나에게 맡기고, 정말 말한 대로 하는지 확인합니다. 가스레인지 손잡이를 떠올려 보세요. 손잡이를 "3"에 맞추면 불이 그만큼 나옵니다. DAC는 board가 말한 숫자(0–4095)만큼 전압을 내는 손잡이이고, ADC는 반대로 전압을 보고 숫자로 적는 눈금자입니다. 둘을 이으면 board가 자기가 낸 전압을 자기가 다시 읽을 수 있습니다. 그 숫자가 맞는지는 멀티미터로 대조합니다. 아직 소자는 없습니다.

할 일 하는 곳 결과로 보는 것

I²C 스캐너 Arduino IDE 칩 주소 두 개 (0x48, 0x6x)
DAC·ADC 대조 Arduino IDE + 멀티미터 코드 2048 → 약 1.65 V

DAC (digital-to-analog converter): 숫자를 전압으로 바꾸는 칩. MCP4725는 0–4095의 숫자(코드)를 받아 0–3.3 V 사이의 전압을 냅니다. 코드 2048이면 절반인 약 1.65 V.

ADC (analog-to-digital converter): 전압을 숫자로 바꾸는 칩. ADS1115는 입력이 4개(A0–A3)이고 16 bit(65,536단계)로 읽습니다. 눈금이 65,536개인 자와 같습니다.

연결 (module 핀 이름은 제품마다 다르니 실크 인쇄로 확인): 두 module 모두 VCC→board 3.3 V, GND→GND, SDA→P0.26, SCL→P0.27 (아두이노 모양 헤더의 SDA·SCL 자리). ADS1115의 ADDR→GND(주소 0x48). DAC VOUT → ADS1115 A0. module 전원은 5 V가 아니라 3.3 V에 연결합니다 (5 V로 켜면 SDA·SCL도 5 V가 될 수 있음).

VCC · GND · SDA · SCL · VOUT: module 다리의 이름. 차례로 전원(+), 전원(−, 0 V), 데이터선, 시계선, 출력 전압. module 기판에 흰 글자(실크)로 인쇄되어 있습니다. ADS1115는 VCC 대신 VDD로 적힌 것도 있습니다.

I²C 주소: 같은 두 선(SDA·SCL)에 매달린 칩들을 구별하는 번호. 0x48처럼 16진수로 씁니다. 반에서 출석 번호를 부르면 그 학생만 대답하듯, board는 주소를 불러서 그 칩에게만 말을 겁니다.

이어서 하기. 배선은 breadboard에 꽂힌 채 두면 다음 날에도 그대로 씁니다. Arduino IDE는 File → Open Recent로 마지막 sketch(p3_i2c_scan 또는 p3_dac_adc)를 엽니다.

#include <Adafruit_TinyUSB.h>  // NU40: USB 시리얼(Serial)을 쓰려면 필요 (없으면 링크 오류)
#include <Wire.h>
void setup() {

    if (Wire.endTransmission() == 0) Serial.printf("I2C 주소 0x%02X\n", a);

  Serial.println("끝");
}
void loop() {}

할 일

  1. File → New Sketch → 편집 창 Ctrl+A → Delete → 아래 코드 상자 오른쪽 위의 복사 아이콘 → Ctrl+V.

#include <Adafruit_TinyUSB.h>  // NU40: USB 시리얼(Serial)을 쓰려면 필요 (없으면 링크 오류)
#include <Wire.h>
#include <Adafruit_MCP4725.h>
#include <Adafruit_ADS1X15.h>
#define DAC_ADDR 0x62  // 바꿀 것: 스캐너에서 본 DAC 주소
Adafruit_MCP4725 dac;
Adafruit_ADS1115 ads;
const uint16_t codes[] = {0, 1024, 2048, 3072, 4095};
void setup() {
  Serial.begin(115200);
  while (!Serial && millis() < 3000) delay(10);
  Wire.begin();  // NU40: P0.26·P0.27
  if (!dac.begin(DAC_ADDR)) { Serial.println("DAC 없음: 주소 확인"); while (1) delay(1000); }
  if (!ads.begin(0x48)) { Serial.println("ADC 없음: 배선 확인"); while (1) delay(1000); }
  ads.setGain(GAIN_ONE);  // 입력 범위 ±4.096 V
}
void loop() {
  for (uint16_t c : codes) {
    dac.setVoltage(c, false);
    delay(200);
    int16_t raw = ads.readADC_SingleEnded(0);
    Serial.printf("DAC 코드 %4u → ADC %6d = %.3f V\n", c, raw, ads.computeVolts(raw));
    delay(3000);  // 이 사이에 멀티미터로 VOUT을 읽는다
  }
}

질문. DAC 코드 2048에서 왜 약 1.65 V가 나올까요? 코드 1024라면 몇 V일까요? 먼저 적어 본 뒤 정답을 봅니다.

MCP4725는 0–3.3 V를 4096칸(코드 0–4095)으로 나눕니다. 한 칸은 3.3 V ÷ 4096 ≈ 0.0008 V(0.8 mV)입니다. 코드 2048은 딱 절반이므로 3.3 V × 2048/4096 = 1.65 V, 코드 1024는 4분의 1이므로 3.3 V × 1024/4096 ≈ 0.825 V입니다. 위 화면의 0.823 V처럼 몇 mV 다른 것은 전원이 정확히 3.300 V가 아니거나 칩마다 조금씩 다르기 때문입니다.

DAC 없음: 주소 확인 → DAC_ADDR을 스캐너 값으로 바꿨는지. ADC 없음: 배선 확인 → ADDR 핀이 GND에 갔는지. 전압이 코드에 비례해 오르지 않으면 VOUT이 A0에 이어졌는지 봅니다.

풀업 확인

module마다 I²C 풀업 저항이 있으면 병렬로 합쳐집니다. 통신이 불안정하면(값이 가끔 튀거나 없음이 간헐적으로 나오면) module 하나만 남기고 시험해 원인을 좁힙니다. 뺄 때는 항상 USB를 먼저 뺍니다.

풀업 저항: I²C 선을 평소에 3.3 V로 당겨 두는 저항. module마다 하나씩 들어 있어서, module을 여러 개 달면 병렬로 합쳐져 당기는 힘이 너무 세질 수 있습니다.

관찰할 점. DAC는 "숫자 → 전압", ADC는 "전압 → 숫자"입니다. 둘을 이으면 board가 자기가 낸 전압을 자기가 읽어 확인할 수 있습니다. 소스미터가 하던 "전압 걸기"는 이것으로 끝이고, "전류 읽기"는 다음 단계의 회로가 더 필요합니다.

다음 단계 조건. 코드 2048에서 멀티미터와 ADC가 모두 1.65 V 근처를 보이면 P3.4로 갑니다.

P3.4. 소자 구동·전류 측정 회로

이제 소스미터의 두 번째 일, "흐르는 전류 재기"를 맡깁니다. 그런데 ADC는 전압만 읽을 수 있습니다. 그래서 전류를 전압으로 바꿔 주는 회로가 하나 더 필요합니다. 수도관을 떠올려 보세요. 관에 흐르는 물의 양은 눈에 안 보이지만, 관 중간에 좁은 구간을 끼우고 그 앞뒤의 수압 차이를 재면 물이 얼마나 흐르는지 알 수 있습니다. 전기에서는 좁은 구간이 저항이고, 수압 차이가 전압입니다.

새 체중계를 받으면 먼저 무게를 아는 1 kg 추를 올려 보듯, 이 회로도 진짜 소자를 꽂기 전에 값을 아는 저항(100 kΩ)과 RC로 맞는 숫자가 나오는지 확인합니다. 이 단계의 마지막 그림(소스미터와 겹쳐 그린 저항·RC 측정)이 P3의 첫 결과이고, 그 전까지 이 회로는 "설계안"입니다.

DAC는 전원이 켜지는 순간 EEPROM에 저장된 코드를 firmware보다 먼저 내보냅니다. 그 사이 V_ref는 아직 0 V에서 오르는 중이라, 소자에 순간적으로 수 V가 걸릴 수 있습니다. 그래서 전원을 켜거나 Upload할 때는 항상 J1을 빼 둡니다.

shunt 저항 (R_s): 전류 길에 끼운 작은 저항. 양끝 전압을 재면 전류를 압니다(I = V ÷ R). 예: 1 kΩ 양끝이 0.01 V면 10 µA. 위 수도관 이야기의 "좁은 구간"입니다.

TIA (transimpedance amplifier): op-amp로 만든 "전류 → 전압 변환기". shunt보다 작은 전류(nA)도 읽습니다. 변환 비율은 피드백 저항 R_f가 정합니다. 예: R_f = 150 kΩ이면 1 µA가 0.15 V가 됩니다.

가상 기준점: TIA의 op-amp가 − 입력을 V_ref와 같게 계속 맞춰 주는 것. 덕분에 소자의 아래쪽 끝이 V_ref에 "붙어 있는 것처럼" 됩니다.

R_f 고르기: 출력이 전원 끝에 닿지 않도록 R_f ≈ 1.5 V ÷ 최대 전류. 예: 최대 10 µA → R_f = 150 kΩ. 이때 ADS1115 ±2.048 V 범위의 한 칸(62.5 µV)은 0.42 nA에 해당합니다.

포화: 전류가 약 1.5 V/R_f를 넘으면 op-amp 출력이 전원 끝에 붙고, 가상 기준점이 깨져 소자 전압도 계산과 달라집니다. ADC는 여전히 범위 안이라 숫자만 보면 모를 수 있어서, firmware는 출력이 기준에서 1.5 V 이상 벗어나면 포화로 셉니다 (데이터 모으기의 Q 줄).

saturation (op-amp 포화): op-amp 출력이 전원 끝(0 V나 3.3 V)에 붙어 더 못 움직이는 것. 버튼 리듬의 조도 포화와 같은 뜻입니다. 이때 숫자는 나오지만 틀린 값입니다.

C_f와 안정성 — R_f·C_f 값만으로 보장되지 않습니다. TIA는 입력에 붙은 용량(C_in: 소자의 큰 계면 용량 + 배선 + op-amp 입력)이 클수록 출력이 떨리기 쉽습니다. 출발점으로 쓰는 근사식:

C_f ≥ √( C_in / (2π · R_f · GBW) ) (GBW: op-amp의 이득-대역폭 곱, MCP6002 약 1 MHz)

C_f: R_f와 나란히 다는 작은 capacitor. TIA 출력이 저절로 떨리는(발진하는) 것을 막는 완충 장치입니다. 너무 크면 대신 반응이 느려집니다.

GBW (gain-bandwidth product, 이득-대역폭 곱): op-amp가 얼마나 빠른 신호까지 따라가는지를 나타내는 값. MCP6002는 약 1 MHz. 클수록 빠른 op-amp입니다. 식에 넣는 숫자로만 알면 됩니다.

예: C_in = 0.5 µF(가정), R_f = 150 kΩ → C_f ≥ 약 0.7 nF. 그리고 응답 시간(대략 5 × R_f × C_f)이 pulse 폭 θ보다 충분히 짧아야 합니다: 150 kΩ × 6.8 nF × 5 ≈ 5 ms ≪ 50 ms. C_in은 모르는 값이므로 실측으로 확인합니다 (저항으로 검증). op-amp 입력 오프셋(수 mV) 때문에 0 V에서도 전류가 0이 아니게 보일 수 있으니, 0 V에서 잰 값을 빼는 영점 보정을 합니다.

저항·RC로 회로를 먼저 검증

이 카드 묶음의 목적: 진짜 소자를 꽂기 전에, 값을 아는 저항(100 kΩ)과 RC로 회로가 맞는 숫자를 내는지 확인합니다. 쓰는 firmware는 B4_test입니다. Serial Monitor에 글자 하나를 입력해 명령합니다: s = 전압 계단 시험, c = DAC 보정, e = EEPROM에 안전 코드 저장.

RC 모의 소자: 저항(R)과 capacitor(C)를 나란히 단 것. 전압을 바꾸면 전류가 천천히 자리 잡는 "느린 소자" 흉내입니다. 진짜 소자를 꽂기 전에 회로를 시험하는 데 씁니다.

실제로 계산한 기대(100k)와 측정 전류가 몇 % 안에서 같으면 회로가 맞는 것입니다. 0 V에서 몇 nA가 남는 것은 op-amp 오프셋이며, 영점 보정으로 뺍니다. 다섯 줄을 복사해 연구 노트에 붙여 둡니다(소스미터와 겹쳐 그릴 때 씀).

질문. 요청 +0.500 V 줄에서 기대(100k)는 왜 약 +4996 nA일까요? 그리고 요청 +0.000 V인데 전류가 +3.10 nA인 것은 고장일까요? 먼저 적어 본 뒤 정답을 봅니다.

옴의 법칙 I = V ÷ R입니다. 실제로 걸린 전압 0.4996 V를 100 kΩ(= 100,000 Ω)으로 나누면 0.000004996 A = 4.996 µA = 4996 nA입니다(1 µA = 1000 nA). 요청한 0.500 V가 아니라 실제 값으로 계산하는 이유는, DAC가 낸 전압과 저항에 걸린 전압이 조금 다르기 때문입니다.

고장이 아닙니다. op-amp는 입력이 0이어도 출력이 몇 mV 어긋나 있는 버릇(오프셋)이 있습니다. 이것이 몇 nA처럼 보이는 것입니다. 저울에 아무것도 안 올렸는데 3 g이 나오면 영점을 맞추듯, 0 V에서 잰 값을 다른 값에서 빼면 됩니다(영점 보정).

거부됨 → 요청 전압이 V_LIMIT(1.0 V)을 넘은 것. [포화]가 붙음 → R_f가 너무 커서 출력이 전원 끝에 붙은 것. R_f를 줄입니다(줄인 값은 device_io.h의 R_MEAS에도). 전류가 일정 비율로 다르면 R_f 실제 값과 DAC 보정을 봅니다.

R–C 자리에 소자를 꽂을 때: 부품만 바꾸면 되나

사이드 프로젝트와 R–C 첫 배선에서는 "R–C 자리에 소자를 꽂으면 같은 질문을 할 수 있다"고 했습니다. 질문은 같지만, 회로는 그대로 두고 부품만 바꾸면 되는 경우는 드뭅니다. 먼저 이 회로가 하는 일을 두 줄로 정리합니다.

  • 거는 것: DAC가 만든 전압 pulse. 소자 아래쪽이 V_ref(약 1.65 V)에 붙어 있어서, 소자에는 DAC 전압 − V_ref가 걸립니다(R_lim에서 떨어지는 만큼 덜).
  • 읽는 것: 소자를 지나간 전류. TIA(또는 션트 저항)가 전류를 전압으로 바꾸고, ADS1115가 그 전압을 숫자로 읽습니다. R–C 첫 배선처럼 capacitor 전압을 바로 읽는 것이 아닙니다.

아래 조건 중 하나라도 맞으면 소자 앞뒤의 회로(interface)를 바꾸거나 더해야 합니다. 모두 확인 전의 조건이며 사실이 아닙니다. 내 소자에 해당하는지는 P2.1에서 잰 특성(전류 범위, 필요한 전압, 저항)으로 판단합니다 [실물 미검증].

조건 (이러면) 왜 문제인가 무엇을 바꾸나
소자 전류가 TIA 범위 밖: 최대 전류 × R_f가 약 1.5 V를 넘거나, 전류가 너무 작아 ADC 숫자가 몇 칸밖에 안 움직임 크면 op-amp 출력이 전원 끝에 붙어(포화) 숫자가 틀림. 작으면 noise에 묻힘 R_f를 바꿈: R_f ≈ 1.5 V ÷ 최대 전류. 바꾼 값은 device_io.h의 R_MEAS에도. 10 nA보다 작으면 breadboard TIA로는 어려움(전류 측정의 표)
소자에 양·음(bipolar) 전압이 필요한데, DAC는 0–3.3 V만 냄 소자 아래쪽을 GND(0 V)에 붙이면 + 쪽만 걸 수 있음 이 설계처럼 아래쪽을 V_ref(1.65 V)에 두어 약 ±1 V까지. 그보다 넓은 범위가 필요하면 음전원 op-amp 회로나 계측 중심 대안(AFE 평가보드·퍼텐쇼스탯)
소자 임피던스가 큼: 같은 전압에서 전류가 nA 이하 큰 R_f가 필요해 반응이 느려지고, op-amp 입력 바이어스 전류·누설·배선 noise가 상대적으로 커짐 입력 바이어스가 작은 op-amp(예: LMC6482), 짧은 배선·차폐. 그래도 안 되면 소스미터 유지
소자가 합선될 수 있거나 허용 전류가 작음 이 회로에는 compliance가 없음 직렬 전류 제한 저항 R_lim을 꼭 둠: 3.3 V ÷ R_lim ≤ 허용 전류. 대신 R_lim × 소자 용량만큼 pulse가 느려지므로 소자 전압을 A0로 재서 씀

R–C 첫 배선 회로(P1.04 → 저항 → capacitor)에는 소자를 꽂지 않습니다. P1.04는 0 V와 3.3 V 두 값만 내고, 전류 제한도 없고, 전류가 아니라 전압을 읽기 때문입니다. 소자는 이 단계의 회로(R_lim·J1·TIA)를 저항·RC로 검증한 뒤 P3.5에서 꽂습니다.

P3.5. board로 reservoir 데이터 모으기

같은 노래를 휴대폰 마이크와 방송용 마이크로 녹음하면, 노래는 같아도 소리 크기와 잡음이 조금씩 다릅니다. 소자도 그렇습니다. P2에서 소스미터로 잰 숫자와 이 회로로 잰 숫자는 같은 소자라도 조금씩 다르므로(gain·offset이 다름), P2에서 학습한 weight는 이 회로에서 맞지 않을 수 있습니다. 그래서 이 회로로 다시 잽니다. PC가 입력을 하나씩 board로 보내고, board가 pulse를 걸고 전류를 읽어 돌려줍니다.

gain (이득): 측정 장치가 실제 값을 몇 배로 읽는지. 예: 실제 10 nA를 한 장치는 10.0, 다른 장치는 10.3으로 읽으면 gain이 3 % 다릅니다.

offset (오프셋): 0이어야 할 때 남는 값. 예: 전류가 0인데 3 nA로 읽힘.

weight: 학습이 끝난 "판단 식"의 숫자들. PC 없이 판단에서 자세히 봅니다.

config.h: board가 읽는 설정 파일. 실습 4가 설정 파일(json)에서 숫자를 옮겨 만듭니다.

# ============================================================
# 3. mock board: B5_collect firmware가 하는 일을 컴퓨터 안에서 흉내
# ============================================================
#
#   진짜 board                          mock board
#   DAC로 전압 걸기                     MockSMU(가짜 소자)에 전압 걸기
#   pulse 끝에 TIA·ADC로 전류 읽기      가짜 소자의 전류를 nA로
#   A0−A1로 실제 소자 전압 읽기         건 전압 − 전류 × R_lim (R_lim에서 떨어지는 만큼)
#   micros()로 pulse 시간 재기          가상 시계라 정확히 50 ms
#
#   가짜 소자(model "memory")는 전압을 받으면 전도도가 천천히 오르고 0 V에서
#   τ = 0.5초로 돌아오는 '장난감'이다. 진짜 소자의 성능과는 상관없다.
# ============================================================

class MockBoard:
    def __init__(self):
        self.dev = MockSMU(model="memory", R=1e6, tau=0.5, compliance_A=1.0,
                           v_limit_V=cfg["instrument"]["v_limit_V"], read_dt=0.005)
        self.dev.enable()
        self.R_lim = cfg["instrument"]["R_lim_ohm"]
        self.R_meas = cfg["instrument"]["R_meas_ohm"]

    def measure_trial(self, n, u_row):
        self.dev.reseed(n)                              # 같은 trial은 같은 잡음
        self.dev.hold(0.0, enc["rest_s"])               # 0 V로 쉬기 (rest)
        S, V, sat = [], [], 0
        for v in pulse_plan(u_row, enc):                # pulse 48개
            last = self.dev.hold(v, enc["theta_s"])[-1]  # pulse 끝의 읽기
            i_A = last["I"]
            S.append(i_A * 1e9)                         # 전류 (nA) = state
            V.append(v - i_A * self.R_lim)              # 실제 소자 전압
            sat += abs(i_A * self.R_meas) > 1.5         # TIA 출력이 1.5 V를 넘으면 포화로 셈
        P = np.full(NF, theta_us)                       # 명령 유지 시간 (µs)
        return np.array(S), dict(I_nA=np.array(S), V_dev=np.array(V), period_us=P,
                                 read_end_us=P.copy(), saturated=np.array([sat]))

줄 뜻 단위
S pulse 끝 전류 (state) nA
V pulse 끝에 잰 실제 소자 전압 (A0 − A1) V
P 그 전압 명령이 유지된 시간 µs
R 명령 시작 → 전류·전압 읽기 끝 µs
Q 측정 범위를 벗어난(포화) 읽기 수 개

P는 "명령"이 유지된 시간이지 "소자에 목표 전압이 걸린 시간"이 아닙니다. 소자에 실제로 걸린 전압은 V 줄로 봅니다. mock board는 가상 시계라 P가 정확히 50,000 µs(50 ms)이고, 진짜 board는 micros()로 잰 값이라 조금 다를 수 있습니다 [실물 미검증].

P3.6. PC 없이 판단하고 알리기

운전 연수를 떠올려 보세요. 처음에는 옆자리 강사(PC)가 "지금 브레이크" 하고 판단해 줍니다. 연수가 끝나면 강사가 내리고, 배운 규칙을 머릿속에 넣은 채 혼자 운전합니다. 이 단계도 같습니다. PC에서 학습한 판단 규칙(weight)을 board에 넣고, board가 PC 없이 시험 입력을 재생 → 측정 → 판단해 LED·부저·OLED·휴대폰으로 알리게 합니다.

feature: 판단에 쓰는 숫자 하나하나. 여기서는 pulse 끝에 잰 전류(state)입니다.

weight: 학습이 끝난 "판단 식"의 숫자들. feature마다 weight를 곱해 모두 더하면 점수가 나옵니다. 예: feature 2개가 (10, 4), weight가 (0.3, −0.5)면 점수 = 10 × 0.3 + 4 × (−0.5) = 1.0.

class: 판단의 답 번호. 여기서는 0 또는 1. 점수가 0보다 크면 class 1, 아니면 class 0입니다.

실습 6. 판단 식 학습 (p3_6_readout.py)

실습 5에서 모은 state 중 마지막 4칸의 16개(4칸 × mask 4개)만 보고 class 0인지 1인지 맞히는 판단 식을 학습합니다. P1.2의 "마지막 4칸만 보고 맞히기"와 같은 질문을 board 측정 데이터에 묻는 것입니다. 연습 56개로 weight를 정하고, 한 번도 안 본 시험 24개로 채점합니다.

balanced accuracy: class 0 문제와 class 1 문제를 따로 채점해서 평균낸 정확도. 한쪽 답만 계속 찍는 꼼수는 1.0과 0.0의 평균 0.5가 되어 들통납니다. chance는 0.50.

confusion matrix: 정답(줄)과 판단(칸)의 개수 표. 대각선(왼쪽 위·오른쪽 아래)이 맞힌 수입니다.

label shuffle: 정답지(label)를 일부러 무작위로 섞은 뒤 똑같이 학습·시험하는 점검. 정답이 엉망이니 0.50 근처가 나와야 정상입니다. 20번 섞어 평균과 흩어진 정도(±)를 냅니다.

C: 학습할 때 weight를 얼마나 크게 허용할지 정하는 손잡이. 프로그램이 연습 데이터 안에서 여러 값을 시험해 보고 고릅니다.

# 1. 바꿔 볼 수 있는 설정값  ← 여기를 바꿔 보세요
# ============================================================

실습 7. board용 파일 내보내기와 자기 점검 (p3_7_export.py)

board는 Python을 돌릴 수 없습니다. 그래서 판단 식을 숫자 표(헤더 파일 네 개)로 바꿔 board 코드와 함께 올립니다. 이 실습은 그 파일을 쓰고, board가 켜질 때 하는 자기 점검(같은 feature를 넣으면 board도 Python과 같은 점수를 내는가)을 PC에서 먼저 해 봅니다.

헤더 파일 (.h): board 코드가 읽는 작은 글 파일. weight·설정·시험 입력을 숫자로 적어 sketch와 함께 board에 올립니다. 시험 볼 때 들고 가는 요약 쪽지와 같습니다.

self-check (자기 점검): board가 켜질 때, 미리 저장해 둔 feature 5개로 점수를 계산해 Python이 같은 feature로 낸 점수와 비교하는 것. 같은 문제를 계산기 두 대로 풀어 답을 맞춰 보는 것과 같습니다.

float32: board가 쓰는 소수 형식. Python 기본(float64)보다 자릿수가 적어서 점수가 아주 조금(0.000001 정도) 다를 수 있습니다.

P3.7. 시간과 에너지를 공정하게 재기

상황. 자동차는 신호 대기 중에도 엔진이 돌며 기름을 씁니다. 그래서 "서울에서 부산까지 기름 얼마"라고 할 때 대기 중에 쓴 것까지 넣는지에 따라 숫자가 크게 달라집니다. board도 같습니다. 이 단계에서는 "board가 판단 하나에 얼마나 걸리고 얼마나 쓰는가"를 세 가지로 나눠 재고, 소자 없이 MCU만으로 할 때와 비교합니다.

대기 전력: 아무 일도 안 할 때 board·회로가 쓰는 전력. 신호 대기 중인 자동차의 기름처럼, 판단할 때만 쓰는 전력과 구분합니다.

mWh: 전력(mW)에 시간(h)을 곱한 에너지 단위. 100 mW를 1시간 쓰면 100 mWh. USB 전력 측정기가 누적해 보여 줍니다.

무엇 정의 재는 법
전체 에너지 판단 하나 동안 전원에서 나간 에너지 (대기 포함) USB 전력 측정기 mWh 차이 ÷ 판단 수
추가 에너지 (처리 중 전력 − 대기 전력) × 처리 시간 같은 측정기, 대기·처리 구간 분리
소자 단자 에너지 ∫ V_소자 · I dt (부호 포함) 측정한 전압·전류로 계산

소자 단자 에너지: 소자 양끝에 걸린 전압 × 흐른 전류를 시간마다 더한 것. 소자 "자체"가 쓴 에너지입니다. 예: 0.5 V × 5 µA를 0.05 s 동안 = 0.000000125 J(0.125 µJ).

  • 어디까지 포함했는지 적습니다: 쉬는 시간, 기준 전압 회로, 통신, 알림, (P3.8이면) ECG module·R파 검출.
  • USB 전력 측정기의 해상도(예: 1 mA 단위)로 처리 중·대기 차이를 구별할 수 있는지 먼저 봅니다. 구별되지 않으면 "측정 한계 이하"로 적습니다.
  • 비교 대상: MCU만으로 같은 입력·같은 정확도 조건에서 판단할 때(예: 입력 25점에 같은 선형 분류기)의 시간·에너지.

관찰할 점. 에너지의 대부분은 board·ADC·DAC가 쓰고 소자 몫은 작게 나올 가능성이 큽니다. 그렇게 나오면 판독 횟수를 줄이는 소자, 디지털화 전 처리, 깊은 절전이 왜 중요한지를 숫자로 보인 것입니다.

P3.8. (선택) ECG 신호로 도전

기본 경로: 사람 없이

ECG 시뮬레이터, 또는 두 번째 board가 MIT-BIH 파형을 재생해 분압기(예: 100 kΩ : 100 Ω, 약 1/1000)로 mV 수준으로 줄여 AD8232 입력에 넣습니다. P3.8은 사람에게 연결하지 않고 끝낼 수 있게 되어 있습니다.

ECG (electrocardiogram, 심전도): 심장이 뛸 때 몸 표면에 생기는 작은 전압(약 1 mV). R wave는 그중 가장 뾰족한 봉우리입니다.

AD8232: ECG 신호를 키워 주는 module. 의료기기가 아닙니다.

ECG 시뮬레이터: 사람 대신 ECG 모양의 전압을 내는 장치. MIT-BIH는 공개된 실제 ECG 기록 모음입니다.

분압기: 저항 두 개로 전압을 일정 비율로 줄이는 것. 100 kΩ : 100 Ω이면 약 1/1000이라, board의 1 V가 1 mV가 됩니다.

AD8232의 RL은 단순 접지가 아니라 오른다리 구동(right-leg drive) 출력입니다. 몸의 공통 전압을 능동적으로 맞춰 noise를 줄이는 출력이므로, 시뮬레이터 연결도 제조사 안내대로 합니다.

경고사람 몸에 연결하는 것은 별도 관문

사람 연결에는 절연, 누설 전류, 전원·데이터 경로, 입력 보호 설계가 필요하고, 배터리로 바꾸거나 USB를 뽑는 것만으로 안전해지지 않습니다. 의료 전기안전에 경험이 있는 사람의 검토를 받은 뒤에, 연구 데이터로 쓸 경우 KAIST IRB 승인과 함께 진행합니다. 이 시제품과 AD8232 module은 의료기기가 아닙니다.

두 경로를 정확히 구분하기

  • 경로 1: 소자는 디지털화 뒤의 보조 처리기입니다. 엣지 컴퓨팅이긴 하지만 "디지털화 전에 처리"하는 이점은 없습니다.
  • 경로 2: 신호가 숫자가 되지 않고 소자에 들어가며, ADC는 reservoir state만 읽습니다. 아날로그 스위치로 만든 mask(켜짐/꺼짐)는 DAC mask(높이 조절)와 입력 모양이 다르므로 PC 없이 판단의 weight를 그대로 쓸 수 없고 다시 측정·학습합니다.

near-sensor (센서 옆에서 처리): 신호를 숫자로 바꾸기 전에 아날로그 그대로 처리하는 방식. 경로 2가 이것입니다. 숫자로 바꾸는 일(ADC)이 줄어 전기를 아낄 수 있다는 것이 기대하는 이점입니다.

연속 처리에 필요한 조건 (계산 먼저)

심장 박동은 약 0.6–1초마다 옵니다. 지금 설정(박동 하나 ≈ 7초)으로는 박동이 쌓이기만 합니다. 연속 처리하려면:

  • 처리 시간 ≤ 박동 간격: L × M × θ + 쉬기 ≤ 약 0.6 s. 예: L=25, M=1, θ=20 ms → 0.5 s, 쉬기 없이. 그러려면 소자의 흔적이 20 ms 규모에서 의미 있게 변해야 합니다 (P2.1에서 확인할 것).
  • ADS1115 변환 예산: 최대 860회/초는 모든 채널을 합친 예산입니다. ECG를 250 Hz로 읽으면서(경로 1) pulse마다 전류도 읽으면 두 일이 같은 예산을 나눠 씁니다.
  • 버퍼·누락 정책: 처리가 밀리면 어떤 박동을 버릴지 정하고, 그 비율을 기록합니다.
